# 記録テキストの暗号化 — 設計

作成日: 2026-08-06
状態: **未着手。判断待ち。**

写真は 2026-08-06 に端末へ移した。同じ問題がテキストにもある。
ただし移し方が違うため、別に設計する。

---

## 1. 何が問題か

記録は Supabase に平文で保存されている。
**サーバーの鍵（`service_role`）を持つ開発者が、全員の記録を読める。**
Supabase の管理画面からも読める。

認可の設計では消せない。置き場所そのものの問題である。

---

## 2. 写真と同じ手は使えない

写真は端末へ移せた。テキストは移せない。
**サーバー側のテキストに依存している機能が多すぎる。**

| 機能 | 依存 |
|---|---|
| 保存後のAI応答 | `/save` がその日と直近の記録を読む |
| 今日の灯り | 前日の記録を読む |
| 今週・今月の振り返り | 期間の記録を読む |
| 過去との対話 | 対象期間と当日の記録を読む |
| キーワード | 期間の記録を読む |
| 動画・配信の観察 | 記録と投稿を突き合わせる |
| 計測 | 全記録を読む |

端末へ移すと、Lantern の中身がほぼ無くなる。

---

## 3. 取りうる形

**端末で暗号化し、サーバーには暗号文だけを置く。**
AIに渡すときは、そのときだけ平文を送る（保存はしない）。

```
端末: 平文 → 暗号化 → サーバー（暗号文を保存）
端末: サーバー（暗号文）→ 復号 → 表示
端末: 平文 → サーバー → Anthropic（保存しない）→ 応答
```

開発者が見るのは暗号文になる。
Anthropic には今も送っており、そこは変わらない
（送らなければAIが動かないため、これは仕様の一部）。

### 鍵の置き方

素直な形は「データ鍵をパスワード由来の鍵で包む」。

1. 初回サインアップ時にランダムなデータ鍵を作る
2. パスワードから導出した鍵でデータ鍵を包み、サーバーに保管する
3. ログイン時にパスワードから鍵を導き、包みを解いてデータ鍵を得る
4. データ鍵は端末の安全な領域に置く

サーバーが持つのは**包まれたデータ鍵**だけなので、
パスワードを知らない限り開けない。

**パスワードを忘れると、記録は永久に読めなくなる。**
これは避けられない。暗号化とはそういうものである。

---

## 4. 何を作り替えることになるか

| 対象 | 変更 |
|---|---|
| AI系の6エンドポイント | DBから読むのをやめ、リクエストで平文を受け取る |
| `/api/logs` | 暗号文をそのまま返す（変更小） |
| `/save` | 暗号文を保存する |
| 計測（`scripts/report_metrics.py`） | 暗号文しか読めない。端末で出すか、鍵を渡して復号する |
| クライアント | 暗号化・復号の層、鍵の保管、ログイン時の導出 |
| 検索・カレンダー | すでに端末側。**変更不要** |

検索が最初から端末側だったのは幸いだった。

---

## 5. 失うもの

- **パスワードを忘れたら全記録が読めなくなる。** 再設定では戻らない
- 機種変更のたびにパスワード入力が要る（鍵を導出し直すため）
- 計測が手軽でなくなる
- 実装量が大きく、失敗すると静かにデータを壊す

---

## 6. いつ決めるか

**今の利用者は作者1人。**
開発者が自分の記録を読めることは、それ自体では問題にならない。

問題になるのは**他人が使い始めたとき**。
そして**後から暗号化に移すのは、最初からやるより難しい**。
既存の記録を全部読み出し、暗号化し、書き戻す移行が要る。

したがって分かれ目は **ストア公開の前**。

| 選択 | 意味 |
|---|---|
| 公開前にやる | 実装が重い。公開が遅れる |
| 公開後にやる | 移行が要る。その間の記録は平文で置かれる |
| やらない | プライバシーポリシーに現状を明記して運用する（**現在の状態**） |

現在は3つ目を選んでいる。`PRIVACY.md` に
「提供者が管理者として閲覧できる状態にある」と明記した。
**隠さないことが、暗号化していない状態で取れる唯一の誠実な形である。**

---

## 7. やらないと決めたこと

**サーバー側で鍵を持つ暗号化。**
開発者が鍵を持つので、何も解決しない。「暗号化している」と
言えるようになるだけで、利用者にとっては現状と同じ。
言えるようになるだけの対策は、むしろ有害である。
